# 稿件（写什么，先定稿再分镜）

## 为什么稿子要单独一层

分镜的每一幕 `text` 都该来自稿件，而不是写分镜时临场编。
稿子定了，幕数、幕长、配音、字幕全跟着定；稿子没定就写分镜，等于把"内容"和"排布"一起猜，改一次要动两层。

顺序：**brief 确认 → 定稿件类型 → 写稿 → 用户确认稿 → 写分镜 → 建场景**。

## 先定类型（brief.scriptType）

| 类型 | 是什么 | 什么时候用 | 谁读它 |
|---|---|---|---|
| 口播稿 | 配音要念出来的话 | 口播带货、知识讲解、Vlog 旁白 | 只听不看也懂 |
| 屏幕文案 | 只出现在画面上的字（标题/要点/数据） | 信息图、数据动画、产品参数 | 只看不听也懂 |
| 双轨 | 口播稿 + 屏幕文案各一套 | 大多数商业短视频 | 两套要互补，不能互相复读 |
| 无稿 | 没有文字层，纯画面 + 音乐 | 氛围片、片头、品牌形象 | 不适用 |
| 用户已给稿 | 用户自带文案 | 甲方给了稿、公众号改视频 | 你的活是**改写**，不是重写 |

**双轨最容易写岔**：口播说"这个价格真的离谱"，屏幕上就不能再写"价格离谱"——屏幕上该写具体的 `¥199`。
口播给情绪和逻辑，屏幕给数字和名词。

## 写口播稿

- **能念出来**：写完自己读一遍，读着打结的句子就重写
- **一句一意**：一句话只说一件事，长句拆成两句
- **口语词**：用「这个 / 你 / 咱」这类词，别用「该 / 其 / 予以」
- **数字写阿拉伯数字**：`199`、`3 天`；TTS 会转成中文读法
- **英文缩写写读音**：API → 「接口」或「A P I」，否则逐字母乱读
- **一段一幕**：`save_script` 的 segments 一段对应一幕，后面 `save_storyboard` 直接搬
- 语气先跟用户对齐：朋友聊天 / 专业讲解 / 广告腔 / 情绪独白——同一句话四种语气，成片气质完全不同

## 写屏幕文案

- **字要少**：标题 ≤ 9 字，正文一句 ≤ 18 字（超过就换行或换版式）
- **可断行**：一句能拆成 2–3 个短行，适合逐行入场
- **别写解释**：屏幕上只放结论和数字，解释交给口播
- 一条文案对应一幕，别把三段话塞进一屏

## 字幕（和屏幕文案是两回事）

字幕是「配音说什么就显示什么」，一屏一句、**不带标点、最多 18 字**（字号大时更少）。
写入时会自动拆段，你不用自己加换行；但要**看返回里的拆分预览**，拆得别扭就说明稿子太书面。

- 一屏念不完，就是太长
- 标点只用来在稿子里断句，不上屏
- 一屏停留 ≈ 每字 0.22–0.3 秒（3.5–4.5 字/秒），快了就是闪一下
- 完整规则 / 老工程怎么批量修：`get_guide("subtitle")`

## 字数 ↔ 秒数

中文口播约 **4.5 字/秒**（短视频偏快，可到 5.5）：

- 30 秒 ≈ 135 字
- 60 秒 ≈ 270 字
- 15 秒 ≈ 68 字

`save_script` 会按这个给你每段预估秒数，并和 `brief.durationSec` 对比。
差 25% 以上会提示——**这时候是改稿还是改时长，要问用户**，别自己砍句子。

## 三个硬规矩

1. **稿子必须给用户看**：`save_script` 之后把整段稿发出去（每段带预估秒数），点头后 `confirm_script`。
   没确认过，`build_storyboard` 会拒绝（`scriptType=无稿` 除外）。
2. **改稿即失效**：`save_script` 会清掉上一次的 `confirmedAt`，改完要重新请用户确认。
   别拿"上一版他同意了"当这一版的通行证。
3. **事实要核**：价格、日期、地点、产品参数、资质说法——用户没给的一律不编；
   稿子里出现事实性数字，就在发稿时单独列一行"这几个数你核一下"。

## 常见坑

- 稿子写得漂亮但读不顺 → TTS 出来一顿一顿。写完朗读一遍再发。
- 双轨两套话打架 → 口播和屏幕各说一遍同一件事，观众信息过载。
- 稿子超时长硬砍 → 砍掉的是铺垫，留下的是干结论，节奏全塌。宁可砍一整段。
- 用户给的稿照抄 → 书面语进旁白，听着像念公文。该改写就改写，但改完要标出改了哪里。
